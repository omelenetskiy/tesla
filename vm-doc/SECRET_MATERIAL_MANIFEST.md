# DriveScope VM Secret Material Manifest

This file is an LLM-safe inventory of the private material required to rebuild the DriveScope Oracle Cloud VM. It intentionally contains **no secret values, no private key contents, no tokens, and no client secret values**.

Never put real secrets in this repository or in `vm-doc/`. Store them in an approved password manager, encrypted offline backup, or the VM's protected filesystem.

## 1. Local operator SSH key

| Item | Value |
|---|---|
| Local path | `~/.ssh/ubuntu-ssh-key-2026-09-14.key` |
| Used for | SSH and `scripts/deploy.sh` |
| Target | `ubuntu@130.61.30.119` |
| Required mode | `0600` |
| Repository status | Must never be committed |

Check without printing contents:

```bash
test -f ~/.ssh/ubuntu-ssh-key-2026-09-14.key
chmod 600 ~/.ssh/ubuntu-ssh-key-2026-09-14.key
ssh-keygen -lf ~/.ssh/ubuntu-ssh-key-2026-09-14.key
```

If this key is lost, provision a new authorized key through the Oracle Cloud console or an existing administrator path. Do not regenerate it by overwriting a production key without confirming access and rollback.

The VM keeps its own `/home/ubuntu/TeslaApp/.env`. It is excluded from rsync and must be restored manually from the secret manager.

Required server-side values:

```text

SUPABASE_SERVICE_ROLE_KEY

NEXT_PUBLIC_MAP_STYLE_URL_DARK (optional)

```

Use `.env.example` as the non-secret shape reference. Never copy `.env` into git, chat, issue trackers, screenshots, or build artifacts.

Recommended VM permissions:

```bash
cd /home/ubuntu/TeslaApp
chmod 600 .env
chown ubuntu:ubuntu .env
```

Validate only names, never values:

```bash
awk -F= '/^[A-Z0-9_]+=/ { print $1 }' /home/ubuntu/TeslaApp/.env | sort
```

## 3. Tesla Fleet OAuth material

Required values are issued/configured in the Tesla developer application:

- Fleet region: `na`, `eu`, or `cn`;
- Fleet client ID;
- Fleet client secret;
- exact redirect URI;
- approved scopes;
- registered app domain;
- Tesla virtual-key pairing state.

The redirect URI must point to:

```text
https://app.omelenetskiy.xyz/api/fleet/callback
```

The value must match the Tesla developer portal character-for-character.

Never expose:

- Fleet client secret;
- access token;
- refresh token;
- authorization code;
- PKCE verifier;
- Supabase service-role key.

Fleet tokens are stored encrypted by the application/database flow. They are not files to place in `vm-doc/`.

## 4. Tesla virtual key pair

Generated by:

```bash
cd /home/ubuntu/TeslaApp
deploy/fleet-telemetry/make-key.sh
```

Expected files:

```text
deploy/fleet-telemetry/keys/private.pem
deploy/fleet-telemetry/keys/public.pem
public/.well-known/appspecific/com.tesla.3p.public-key.pem
```

Rules:

- `private.pem` is secret and must be `0600`;
- `private.pem` must never be served by nginx;
- `public.pem` is not secret;
- the public key served at `/.well-known/appspecific/com.tesla.3p.public-key.pem` must match the private key registered with Tesla;
- replacing the key requires re-registering the partner application and pairing the vehicle again;
- never overwrite an existing production private key casually.

Verify the public endpoint without exposing the private key:

```bash
curl -sS --resolve app.omelenetskiy.xyz:443:130.61.30.119 \
  https://app.omelenetskiy.xyz/.well-known/appspecific/com.tesla.3p.public-key.pem
```

## 5. Telemetry TLS certificate

Expected files on the VM/repository deployment directory:

```text
deploy/fleet-telemetry/certs/fullchain.pem
deploy/fleet-telemetry/certs/privkey.pem
```

The private key is secret. The certificate chain is public-ish but should still be managed as deployment material.

Generation/renewal script:

```bash
cd /home/ubuntu/TeslaApp
TELEMETRY_HOST=telemetry.omelenetskiy.xyz \
CERTBOT_DNS_PLUGIN=<approved-certbot-plugin> \
deploy/fleet-telemetry/issue-cert.sh
```

The production Docker config references:

```text
/etc/fleet-telemetry/certs/fullchain.pem
/etc/fleet-telemetry/certs/privkey.pem
```

Verify certificate metadata without printing private material:

```bash
openssl x509 \
  -in /home/ubuntu/TeslaApp/deploy/fleet-telemetry/certs/fullchain.pem \
  -noout -subject -issuer -dates
```

After restoring them, verify schema access with a safe, read-only application command or Supabase dashboard. Do not echo the values.

## 7. Docker and OS credentials

The VM may also require administrator-managed credentials not owned by this repository:

- `ubuntu` SSH authorized key;
- passwordless `sudo` policy for the deployment operator;
- Docker group membership or Docker sudo access;
- certbot DNS provider credentials;
- DNS provider API token used by the selected certbot plugin;
- Oracle Cloud console access;
- domain registrar/DNS access.

These must be restored from the organization's secret manager. Never add them to `.env.example`, git, or this directory.

## 9. Recovery order

1. Restore DNS records for `app.omelenetskiy.xyz` and `telemetry.omelenetskiy.xyz` to `130.61.30.119`.
2. Restore local operator SSH key or provision a replacement through OCI.
3. Connect to the VM and clone/sync the repository.
4. Restore `/home/ubuntu/TeslaApp/.env` with mode `0600`.
5. Generate or securely restore the Tesla virtual key pair.
6. Restore/issue telemetry TLS certificates.
7. Verify nginx routing and the Tesla public-key endpoint.
8. Run `npm ci` and `npm run build` on the VM.
9. Start Docker telemetry services.
10. Start PM2 `TeslaApp` and `TeslaTelemetryIngest`.
11. Verify raw events, snapshots, checkpoints, and trips in Supabase.
12. Run `npm run telemetry:backfill-history` only after schema and credentials are verified.

## 10. Mandatory LLM safety rules

An LLM must:

- never request or print the value of a secret;
- never create a fake token or key;
- never commit `.env`, private keys, certificates' private halves, or API credentials;
- never overwrite a production Tesla private key without explicit confirmation and a pairing plan;
- never expose ports `3000`, `4269`, `4443`, `8443`, or `9090` publicly;
- verify the target VM and path before using rsync;
- run a dry-run before a destructive sync;
- preserve `.fleet-telemetry` during deployment;
- report command output that contains credentials only after redaction;
- use the operational procedures in `ORACLE_CLOUD_VM_OPERATIONS.md` as the source of truth.
